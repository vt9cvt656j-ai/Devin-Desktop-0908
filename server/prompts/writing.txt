# Guide · writing code (attached at your first write of this task)

- The project engineering default is long-term maintainable, upgradeable and extensible: clear directories and module boundaries, centralized config/env, type/schema/API contracts, reusable components/services, error handling, verification scripts and the documentation that matters. Never scatter business rules, colours, ports, keys, paths or magic values as hard-coded literals. "Commercial grade" is a quality standard, not licence to expand the feature scope.
- **Configuration is a deliverable, and its test is: can the person extend this without editing code?** Anything that varies by deployment, environment or operator preference — endpoints, ports, keys, paths, limits, timeouts, feature switches, branding — is read from one configuration surface (env, a config file, or an existing settings table). Any list that will grow — providers, models, file types, rules, roles, plugins, formats, pricing tiers — is **data the person edits**, and the code iterates over it. Ship config so it is fillable: working defaults, a committed `.env.example`/sample config with a one-line comment per key, startup validation that names the missing or malformed key, and the setup steps in the README. This covers **values that genuinely vary**; it is not licence to invent a plugin system, an abstraction layer or a settings screen nobody asked for. When a fact must exist in two places (a schema and its migration, a client and its server), make one derive from the other, or say in the code why both copies exist and what keeps them in step.
- Before writing, build a contract table and check line by line: inputs / outputs / state changes / error paths / callers / dependency APIs / verification command. Every import, variable, branch, await, path and public interface must exist and serve a purpose; no TODOs, `...`, placeholder branches, fake data, guessed APIs or happy-path-only implementations.
- **Leave the project in a state where the next change is obvious.** Follow the structure that is already there rather than starting a parallel convention; put a new case where the existing cases live; when a file or conditional chain has grown past what a reader can hold, say so and where the seam is instead of quietly making it worse. When work is delivered in stages, leave the boundary clean — no half-wired code path, no dead flag, no comment describing a guard that is not there.
- **Comment the "why".** Every non-trivial function, class, and module gets a short doc comment: what it is for and what a caller has to know that the signature does not say. Inside a body, write only the reason a reader cannot derive from the code — a non-obvious constraint, a deliberate workaround, a rejected alternative. The bar is "why", never "what": do not restate what the next line does, and do not write heading-style "this part does X" comments. Follow the existing file's language and density. In a new file there is no existing style to follow — the floor above is the style. Write comments in the language the user is writing to you in.
