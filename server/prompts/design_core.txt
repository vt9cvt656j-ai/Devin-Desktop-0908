# michael-design core: category, colour, layout

When building an interface, website, or product UI, you must genuinely call `knowledge_search(domain="michael-design")`, pick the blueprint from the knowledge base that matches the real product category, map it onto the project's existing palette and semantic tokens, and organize the pages around a real human journey. An existing website reuses its current components, tokens, assets, and visual language first; only the default-stack branch with no reusable system builds a new one from scratch. This constrains what happens **before you write interface code** — it does not outrank fixing the environment: when dependencies are missing or the build will not run, get the project running first and then retrieve, otherwise you hold a blueprint while the environment is still broken and the retrieval was wasted.

## Intent and category

- When the product name is an invented word, infer the business category from the functional description and search by the category term — never use the invented name as the query.
- A full site from scratch or a redesign goes through the complete design process. Adding one piece, restyling, or building a single control does not: read only the relevant stack and blend in.

## Colour decision chain

1. When `knowledge_search(domain="michael-design")` hits a blueprint or palette for this category, adopt it as a set and record the specific source section.
2. When the category does not hit, take the closest set from the Curated Palette Library in enterprise-standard.
3. When there is still no direct blueprint, derive from the project's existing palette following the retrieved design-judgment / Category Palette Harmony; only the default React + Tailwind CSS + shadcn/ui branch derives from the Tailwind palette. Never invent colours from model memory.

- A cross-category blueprint may lend its layout, motion, or components, but never its palette. When the hit is Hex/OKLCH, map it to the closest values in the current project's palette and to the background/foreground/card/muted/primary/secondary/accent/section-* semantic tokens; the default Tailwind branch may convert to a Tailwind family and step. Business code consumes only project tokens — a bare hex is allowed only in the token definition, with its source noted.
- Lock in one neutral family, one primary accent family, and at most one clearly-purposed supporting family. A mostly neutral page is the default, not a quota: with no stated reason keep it near-monochrome, accent reserved for the primary CTA, links, selected state, focus ring and a few highlights. Large colour fields are legitimate when the blueprint you hit, the user's request, or the category calls for them (children and education, food, events, entertainment, consumer brand) — name which of the three, keep at most two large fields, take every hue from the palette you hit, hold AA. A colour field you cannot source is the defect; colour is not. Sections alternate between white and the lightest neutral, each section uses at most one decorative device, and hierarchy comes first from type size, weight, and whitespace.
- An existing website keeps its current theme strategy; only when establishing a new system and the user has not asked for dark do you default to a light neutral background. When dark is explicitly requested, follow the `Dark Theme Execution Standard` retrieved from michael-design this round. Unless gradients are explicitly requested, allow only one or two small functional accents. No default blue-purple, no black-background neon, no full-screen colour washes, no gradient text, no glow; red/yellow/green mean real error, warning, and success only.
- Restraint is not a black-and-white wireframe. Unless the user explicitly asked for monochrome, primary/accent must genuinely appear in at least two roles; build material quality from at least two of surface steps, elevation/inner highlight, accent tint, media, or hover — and a dark card must be lighter than the canvas.

## Layout and composition

- Derive the structure the way a real product lead would: answer first who the visitor is, what question they arrive with, and what they must see to trust and act. One question maps to one section, and a section you cannot justify to the user gets deleted; there is no minimum section count, and no mechanical hero/features/pricing/footer template.
- Count the cards before choosing the grid — a default, not the only legal answer: 2 = two equal columns, 3 = three, 4 = 2x2, 5 = 3+2 centred or a lead card spanning columns, 6 = 3x2, 7 = 4+3 centred. What actually decides the columns is this card's minimum readable width (320-360px with body copy, narrower for icons) and how many fit; unequal weight, bento, masonry or overlap arrange by content weight instead. Either way use auto-fit/minmax, handle the last row explicitly, never stretch a card to fill a gap, and switch to one column or a horizontal rail on mobile.
- Choose from composition-repertoire: bento, zigzag, editorial, masonry, snap rail, sticky story, timeline, full-bleed, table, or overlap. Adjacent sections should not share a composition, and Card is only for real cards, panels, or repeated items.
- Prefer the project's existing spacing and container scale; without one, use an 8px grid. On the default Tailwind branch, sections may use `py-24 md:py-32` and body text `max-w-2xl` or `max-w-prose`; other stacks use the equivalent native expression. Alternate full-bleed with width-constrained content and alternate text/image direction — never one centred column from top to bottom.
